## Password-reset API limitation

The deployed Swagger has `forgot-password`, `reset-password` and the registration `verify-otp` route. The available backend source confirms registration verification rejects an already-confirmed account and consumes email confirmation OTP. It must not be reused to verify reset OTPs.

The UI separates email → OTP → new password → success. With the current deployed API, the OTP step checks six-digit format; **the server verifies the actual OTP only on `reset-password` submission**. The UI explicitly says this. This does not satisfy server verification before showing the password form until the backend supplies a separate endpoint.

To enable strict server gating, set `EXPO_PUBLIC_RESET_OTP_VERIFY_PATH` to a reset-specific POST endpoint accepting `{ email, otpCode }`. It must return the normal successful envelope only when the code is valid, return a failed envelope or 4xx for invalid/expired codes, and preserve the OTP for the subsequent reset request. The frontend then waits for server success before opening the new-password form. Do not configure this to registration `/api/Auth/verify-otp`.

Browser checks use synthetic responses and do not send OTP email or change accounts on Render. Native iOS/Android interactions still require device testing.
